### Гарантии консистентности и отказоустойчивости (Exactly-Once Semantics)

Bublik гарантирует доставку данных по принципу **Exactly-Once** на уровне базы данных, используя комбинацию паттернов *Transactional Outbox* и *Idempotent Consumer*:

1. **Координация чанков на Источнике**: Прогресс миграции отслеживается в изолированной таблице чанков на стороне источника. Статус чанка обновляется только после подтверждения успешной записи от приемника.
2. **Идемпотентность на Приемнике (Outbox)**: На стороне приемника создается таблица `outbox`, где `chunk_id` источника выступает в роли уникального ключа идемпотентности.
3. **Атомарный коммит пайплайна**: При использовании высокоскоростной команды `COPY` в бинарном формате, вставка самих данных и фиксация `chunk_id` в таблице `outbox` выполняются **строго в рамках одной транзакции** на приемнике.
4. **Защита от перезапусков**: Перед обработкой каждого чанка движок Бублика проверяет таблицу `outbox` на приемнике. Если чанк уже был успешно закоммичен в предыдущем аварийном запуске, он бесконфликтно пропускается, исключая появление дубликатов.



#### Высокопроизводительный движок секционирования (Физический CTID + Выравнивание индексов)

Для реляционных баз данных (таких как PostgreSQL) Бублик использует уникальный гибридный подход, который максимизирует скорость чтения и полностью исключает фрагментацию индексов на приемнике:

* **Физическая изоляция страниц (`ctid`)**: Вместо логической пагинации движок источника нарезает данные по физическим адресам строк на диске (`ctid >= ... AND ctid < ...`). Это обеспечивает неблокирующее, молниеносное извлечение данных напрямую из страниц хранения.
* **Оптимизация предварительной сортировки**: Бублик автоматически определяет структуру первичного/кластерного ключа целевой таблицы и добавляет строго соответствующее условие `ORDER BY` (например, `ORDER BY id1, id2`) к запросу извлечения чанка.
* **Нулевая фрагментация на Приемнике**: Передача предварительно отсортированных бинарных пакетов напрямую в команду `COPY` предотвращает расщепление страниц B-Tree индексов на стороне приемника. Данные пишутся строго линейно, сохраняя мгновенную скорость выполнения `COPY` (0.04–0.07 сек на чанк из 30k строк) даже на многогигабайтных таблицах.


#### Умный NoSQL движок секционирования: Адаптивное сэмплирование диапазона токенов

В отличие от стандартных инструментов миграции, которые «вслепую» нарезают кольцо Cassandra, Бублик реализует алгоритм **адаптивного иерархического сэмплирования** для обеспечения равномерного объема чанков (например, целевые 50k строк на чанк) и предотвращения перекосов нагрузки на воркеры:

1. **Сегментация кольца токенов**: Движок миграции определяет текущую топологию кластера и разбивает полное кольцо токенов на первичные диапазоны (Token Ranges).
2. **Двухэтапный сбор статистики (Проба 1/100)**: Для каждого диапазона Бублик выполняет оптимизированную неблокирующую пробу. Он делит диапазон токенов на 10 частей, затем каждую одну десятую делит еще на 10 микро-сегментов (сканируя плотность на уровне 1/100 от диапазона), собирая статистику реального количества строк.
3. **Расчет динамических границ**: На основе собранных метаданных о плотности строк планировщик Бублика вычисляет точные математические границы токенов (`token(...) >= ? AND token(...) < ?`), которые будут гарантированно содержать в районе 50 000 строк в одном итоговом чанке.
4. **Защита от дисбаланса**: При использовании стандартных распределенных ключей партиционирования (например, Murmur3Partitioner), это иерархическое профилирование обеспечивает высочайшую точность. Воркеры Бублика работают синхронно, обрабатывая симметричные объемы данных без простоя потоков.
